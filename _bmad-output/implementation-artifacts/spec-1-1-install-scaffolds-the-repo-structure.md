## Intent

**Problem:** Waypoint has no code yet — no npm package, no CLI entry point, and no `install` command. A consuming repo also has nowhere to put specs, tasks, decisions, role prompts, or Waypoint's own config until `install` creates that structure.

**Approach:** Bootstrap a minimal TypeScript/Commander.js npm monorepo (`packages/cli`, `packages/core`) and implement `waypoint install`, which scaffolds `/specs/{patches,features,systems}`, `/tasks`, `/decisions`, `/roles`, `AGENTS.md`, and `.waypoint/config.yaml` (pre-populated with default patch-classified globs) in the current (consuming) repo, idempotently and safely under concurrent invocation.

## Boundaries & Constraints

**Always:**
- Preserve any path that already exists (file or directory with content) — never overwrite on reinstall, for any of the six scaffolded paths.
- If a scaffolded path exists as a plain file where a directory is expected, exit non-zero with a clear error naming the conflicting path — never crash on a raw filesystem error.
- Two concurrent `install` invocations must not corrupt the scaffold: serialize the writes, or make the second invocation a safe no-op.
- Default-generate `.waypoint/config.yaml` with `tiers.patch` including exactly `specs/patches/**`, `docs/**`, `*.md` (root only), and `tasks/**` — this last entry is load-bearing (Epic 3's `waypoint verify` commit depends on it being patch-classified), not optional.
- Add `.waypoint/.gate-state/` to `.gitignore` (create the file if it doesn't exist; append the line if it does and doesn't already contain it).
- `AGENTS.md` and each of the 4 files under `/roles/` are created as minimal placeholders only (e.g. a one-line "generated by `waypoint install`; content populated by Epic 4" stub) — never fully authored here.

**Ask First:** none anticipated — this story is mechanical scaffolding with no product ambiguity.

**Never:**
- The pre-commit git hook file or any `gate()` logic (Epic 3's scope) — this story does not touch git hooks at all.
- `new-patch`/`new-feature`/`new-system` command logic (Stories 1.2/1.3).
- Real `AGENTS.md` or role-prompt content (Epic 4's scope — placeholders only, see Always).
- A CI pipeline, linter config, or anything beyond the test tooling needed to verify this story.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Fresh install | Empty repo | All six paths created, `.gitignore` updated, no errors | N/A |
| Partial pre-existing | `/specs` already has content | `/specs` content untouched; other paths still created | N/A |
| Path collision | `/tasks` exists as a plain file | Command exits non-zero, error names `/tasks` | Clear message, no partial writes to other paths |
| Concurrent install | Two `waypoint install` run at once | Scaffold ends up correct and non-corrupted | Serialize via a lock, or second run detects completion and no-ops |

## Design Notes

Concurrency doesn't need a distributed lock — a simple `proper-lockfile`-style advisory lock on a marker file (e.g. `.waypoint/.install.lock`) in the target repo is sufficient, since this only ever runs on one machine at a time in practice. If the lock can't be acquired within a short timeout, the second process should treat it as "another install is already running" and no-op rather than error.
