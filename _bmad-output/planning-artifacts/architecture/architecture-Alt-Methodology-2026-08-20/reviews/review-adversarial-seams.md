# Adversarial Seam-Conflict Review — Waypoint

## Overall verdict
The v0.4 redesign genuinely closes every named round 1–3 problem (gate-state/CI-write contradiction, fork-PR token gap, branch-protection deadlock, review-dismissal-on-push, local/CI write race, trailer-grammar/spec-id-encoding gaps, GitHub-specific assumption) by construction, not just by restating intent — CI is now provably read-only and the linkage mechanism no longer depends on parsing anything out of a commit message. But the redesign relocated the ambiguity rather than eliminating it: `waypoint verify`'s self-commit collides with the pre-commit gate it's supposed to satisfy, `runCheck()`'s "verify against a commitSha" contract never specifies how that commit gets materialized on disk, and neither shallow CI checkouts nor squash-merge SHA rewriting is addressed — any of which can make two conforming implementations diverge or make the CI gate permanently unreliable.

## Findings

- **critical** Self-commit vs. pre-commit gate bootstrapping deadlock (§ Data Models → `.waypoint/config.yaml`; § Components → Gate Script & Verification; § Core Workflows step 6) — `waypoint verify` "makes its own commit for that ledger change," and every commit passes through the pre-commit hook, which calls `gate()` with FR7's fail-closed rule: any changed path not glob-matched to the `patch` bucket defaults to Feature-tier enforcement requiring a spec delta in the same diff. The default patch bucket (Story 3.4 AC3, mirrored in the shipped `config.yaml` example) is `specs/patches/**`, `docs/**`, root `*.md` — it does **not** include `tasks/**`. A ledger-only commit therefore changes a Feature-tier-classified file with no spec delta present, which is exactly what `gate()` is defined to block. Two units diverge on how to resolve this undocumented contradiction: (A) hardcode a `tasks/*.ledger.yaml` exemption inside `gate()`'s core logic, silently overriding the config-driven classification FR12 claims is the *only* mechanism; or (B) have `waypoint verify`'s internal commit call `git commit --no-verify` (or equivalent hook-skip), which nowhere appears in the spec and quietly defeats "every commit goes through the same shared gate() regardless of who/what made it" — the document's own stated architectural invariant (§ High-Level Architecture). A third team that implements neither fix ships a `waypoint verify` that fails on first use in any repo following the documented default config. *Fix:* explicitly add `tasks/**` (or the literal ledger glob) to the default/required patch bucket, or explicitly state that `waypoint verify`'s internal commit bypasses hooks by design — either closes the loop, but the document currently states neither.

- **critical** `runCheck()` never specifies how `commitSha` gets materialized before `checkCommand` runs (§ Components → `ledger/`'s second pinned contract — `runCheck()`) — the interface is `{ commitSha, checkCommand } → { ok }`, but nothing says whether an implementation must isolate/checkout that commit (e.g., `git worktree add`) before running `checkCommand`, or whether it's permissible to just run `checkCommand` in whatever the current working directory happens to contain. This is not a cosmetic gap: (A) an implementation that does real isolated checkout is correct for CI's job of re-verifying an arbitrary *historical* `linked_commit` that differs from the PR's current HEAD, but pays a real cost per task (a `checkCommand` like `npm test` may need fresh deps per checked-out commit) that nothing bounds. (B) an implementation that skips isolation and just runs `checkCommand` in-place effectively ignores `commitSha` — for local `waypoint verify` this means "verify against current HEAD" can silently test uncommitted working-tree state rather than the committed snapshot it claims to have checked (a false pass that later disagrees with a clean CI checkout of the same SHA), and for CI's loop over N `done` tasks it means every task is actually being checked against the *same* current PR HEAD regardless of what `linked_commit` says — the "CI independently re-derives correctness from the recorded commit" claim (the redesign's central selling point) becomes a no-op. Two teams building "to the letter" produce either a slow-but-correct checker or a fast-but-meaningless one, and the document can't tell you which one it specified. *Fix:* pin `runCheck()`'s contract to require an isolated worktree/checkout of `commitSha` (and state the dependency-install assumption, or explicitly scope MVP to same-commit-only checks if isolation is deferred).

- **critical** Shallow CI clones and squash-merge silently invalidate `linked_commit` (§ Core Workflows step 7; § Error Handling Strategy → ledger corruption paragraph) — CI re-runs `checkCommand` against each `done` task's recorded `linked_commit` SHA. Two extremely common, individually reasonable configuration choices break this outright and the document addresses neither: (1) default shallow checkouts (`actions/checkout`'s default `fetch-depth: 1`, GitLab's default `GIT_DEPTH`) mean older `linked_commit` SHAs simply aren't present in the CI job's object database — `runCheck()` fails with "unknown revision," not a check failure; (2) squash-merge (a very common default merge strategy) rewrites every feature-branch commit into one new SHA on the target branch the instant a PR merges, so every `linked_commit` recorded during that PR's life becomes unreachable on `main` immediately after merge. The document gives no error-handling semantics distinguishing "commit object not found" from "check genuinely regressed," so one team's CI reports every merged task as a false regression on the very next run (crying wolf, likely trained-out by users), while a team using full-depth clones and rebase/merge-commit workflows never sees the problem — same document, incompatible operational outcomes. *Fix:* either state a required CI-checkout depth/fetch strategy and a merge-strategy assumption, or define `runCheck()`'s "commit not resolvable" as a distinct, non-failing outcome (e.g., re-derive via the squashed merge commit, or skip with a warning) rather than an undifferentiated check failure.

- **high** Self-commit's staging scope is unpinned and collides with a known git gotcha (§ Components → Gate Script & Verification, `waypoint verify` bullet) — "makes its own commit for that ledger change" doesn't say whether the commit is scoped to just the ledger file. Plain `git add <ledger> && git commit` does **not** isolate the commit from other already-staged files — git commits the union of the index plus the given pathspec's working-tree changes, not the pathspec alone (the `--only`/`-o` flag exists precisely to fix this). Implementation A uses naive add-and-commit, silently sweeping any WIP the agent had staged for its own next commit into a `chore(waypoint): verify t1` commit; implementation B uses `git commit --only <ledger-path>` and stays isolated. Both "follow the doc," and they produce different repo histories and different content in the same-named commit. *Fix:* specify that the verify commit must be isolated to the ledger path alone (name `--only`/equivalent explicitly), and state required behavior when other changes are staged at invocation time (proceed and isolate vs. refuse).

- **high** Re-running `waypoint verify` on an already-`done` task is undefined (§ Data Models → Field ownership; § Components → Gate Script & Verification) — v0.3 had an explicit "idempotent never-overwrite-already-verified reconciliation rule" for this exact scenario; the v0.4 changelog describes removing the whole CI-push-back subsystem that rule lived in, and no replacement rule appears anywhere in v0.4. Two units diverge: (A) `verify` treats a `done` task as a no-op or hard error, refusing to touch an already-verified row; (B) `verify` unconditionally re-runs `runCheck()` against the new `HEAD` and overwrites `linked_commit`/the `.gate-state` hash, producing another `chore(waypoint): verify t1` commit. Neither is stated, and they have materially different consequences (B produces silent, repeated ledger/commit churn every time a human double-invokes by habit; A blocks a legitimate re-verify-after-more-commits workflow with no escape hatch mentioned). *Fix:* state explicitly which of no-op / error / re-verify-and-overwrite is correct for an already-`done` task, mirroring the specificity the ownership table gives to first-time writes.

- **high** Bypass-logging guarantee is conditional on infrastructure the document never states as a precondition (§ Core Workflows → "Bypass, reframed"; § Error Handling Strategy → Bypass) — the claim "the only way it lands anyway is a repo admin explicitly merging over a failing CI check, which GitHub/GitLab/etc. already log natively" is only true if the consuming repo has branch protection configured to require the `waypoint gate --ci` check *and* disallow direct pushes to the protected branch. Waypoint doesn't install, verify, or even recommend this configuration anywhere (CI integration is described as "a single script invocation... added to the consuming repo's existing pipeline" — opt-in, unchecked). A repo that runs `npx waypoint install` but never wires branch protection (or a solo developer pushing straight to `main` with no PR at all) can bypass the pre-commit hook with plain `git commit --no-verify` and leave **zero** record anywhere — not a Waypoint log, not a git-host audit entry, because no protected-branch override ever occurred. This directly fails Story 3.1 AC2's "logged, not silent" for a plausible, undocumented-as-out-of-scope class of consuming repos. *Fix:* state the branch-protection-plus-required-check precondition explicitly (ideally have `waypoint install`/`status` detect and warn when it's absent), or scope the "logged, not silent" guarantee's Non-Goal explicitly to PR-gated repos.

- **medium** `.gate-state/<spec-id>.json` update semantics (merge vs. overwrite) are unpinned (§ Data Models → Ledger integrity check) — the example file holds hashes for multiple tasks (`t1`, `t2`) in one JSON keyed by task id. When `waypoint verify` writes the hash for one task, does it read-modify-write (preserving other tasks' previously stored hashes) or write a fresh object containing only the just-verified task's entry? An overwrite implementation silently erases previously recorded hashes for other already-`done` tasks in the same spec — after which the doc's own rule ("no stored hash" behaves like "not checked, same as pending/in-progress") means local corruption detection for those tasks quietly stops working. CI remains a backstop, which is why this is medium rather than critical, but it's exactly the kind of quiet regression the sidecar file exists to prevent. *Fix:* state explicitly that writes to this file are per-task merges, never whole-file replacements.

- **medium** CI's "every `done` task" enumeration has intent but no interface contract, and its cost is unbounded (§ Core Workflows step 7; § Error Handling Strategy; cf. NFR4) — unlike `gate()`, which gets an explicit `GateInput.changedFiles` contract populated by a stated `git diff` invocation, nothing pins *how* CI enumerates "every task the ledger claims is done" (a full `tasks/**/*.ledger.yaml` walk is the clear intent given the stated regression-catching purpose, but no algorithm/interface is given the way `gate()` gets one). Separately, and independently of that ambiguity: `runCheck()` re-runs the full `checkCommand` (e.g. a whole test suite) once per `done` task with no stated deduplication rule for tasks that share an identical `linked_commit`. NFR4 bounds only `gate()`'s file-diff scan (<2s, ≤2000 files/50 specs) — it says nothing about the aggregate cost of N `checkCommand` invocations in CI, which is the more expensive operation by orders of magnitude and grows unboundedly with the number of completed tasks. Two conforming implementations — one deduping by unique `linked_commit`, one naively looping per task — produce identical correctness but wildly different CI runtimes, and neither is wrong per the text. *Fix:* pin the enumeration mechanism explicitly (e.g., glob `tasks/**/*.ledger.yaml` from repo root) and either bound/require dedup of `runCheck()` calls by unique `linked_commit`, or explicitly accept the unbounded cost as a known MVP limitation.

- **low** Push timing for the verify commit is unstated (§ Core Workflows step 6) — nothing says whether `waypoint verify` also pushes its self-commit, or leaves that to the human/agent's next `git push`. Benign in the common case (eventual consistency once pushed), but worth a one-line clarification since CI literally cannot see a `done` status until that commit reaches the remote, which could confuse a first-time user watching CI still show a task `pending` right after a local "verify" reports success.

## Closed / well-pinned (no new finding)
- **Gate-state/CI-write contradiction (round 1–3's headline issue): fully closed by construction.** `.gate-state` is explicitly local-only, gitignored, never expected on a fresh checkout, and CI's correctness check is defined to not touch it at all — there is no longer a file whose committed-vs-not status is ambiguous.
- **Fork-PR token gap, branch-protection deadlock, review-dismissal-on-push, local/CI write race: closed.** All four depended on CI needing write/push permissions; CI is now defined as read-only end to end ("never writes to the ledger, the gate-state file, or anywhere else"), which removes the entire permissions surface these problems lived in.
- **Trailer-grammar and spec-id-encoding gaps: closed.** The commit-trailer linkage mechanism is gone entirely; `waypoint verify <spec-id> <task-id>` takes identity as explicit CLI arguments, so there's no string grammar left to under-specify.
- **Undeclared GitHub-specific assumption: closed.** CI's script needs no elevated permissions and is stated to work identically across providers — true given CI is read-only, unlike the removed push-back design.
- **Async execution ambiguity: closed.** `verify` is explicitly synchronous, with the tradeoff (blocking is acceptable because it's a deliberate, human/agent-chosen checkpoint, unlike the mandatory pre-commit path) stated and justified rather than left implicit.
