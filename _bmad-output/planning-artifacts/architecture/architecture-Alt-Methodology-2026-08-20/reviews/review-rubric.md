# Architecture Quality Review — Waypoint

**Document under review**: `docs/architecture.md` v0.4 (2026-08-20)
**Cross-checked against**: `docs/prd.md` v0.5, `docs/brief.md`
**Review round**: 4 (of a REDESIGN, not a patch)

## Overall verdict

The v0.4 redesign genuinely eliminates the round 1–3 subsystem: the async pre-commit/post-commit split, the `Waypoint-Task:` trailer, the CI push-back write path, the fork-PR token gap, and the branch-protection deadlock are all correctly gone, and most of the rest of the document (tier authority, config schema, drift scope, cross-platform test matrix) remains well-pinned. However, the redesign's own load-bearing new piece — `waypoint verify` writing the ledger and then "making its own commit" — reintroduces a critical bootstrapping conflict with FR7's gate that is of comparable severity to what was removed: a commit containing only the ledger YAML is, by the document's own tier-classification rules, a Feature-tier change with no spec delta in it, which the pre-commit hook (and, on a per-commit basis, CI) would be expected to block. The document never resolves this. Combined with an unbounded CI performance risk in the "done-claim correctness" re-check and an undeclared new assumption (a PR/branch-protection-capable git host) underpinning the bypass-logging story, this round has not actually converged — it traded one set of critical issues in this subsystem for a different one. Verdict: **thin**.

## Findings

- **critical** `waypoint verify`'s own commit is not exempt from the gate it must pass, and the document never notices (§ Components → Gate Script; § Data Models → `.waypoint/config.yaml`; § Core Workflows step 6) — `linked_commit`/`status`/`verified_by_gate` live in `/tasks/<spec-id>.ledger.yaml`. The default patch-classified globs (`specs/patches/**`, `docs/**`, root-level `*.md`, per Story 3.4 AC3) do not cover `tasks/**`, and the Error Handling Strategy explicitly rules out any file→spec association mechanism for non-spec files. So a ledger file, by FR12's own fail-closed rule, defaults to Feature-tier. When `waypoint verify` "makes its own commit for that ledger change," that commit's staged file list is `[tasks/<spec-id>.ledger.yaml]` alone — no spec file, no delta. The pre-commit hook calls `gate()` against exactly that staged list (§ Components → Gate Script: "staged changes only"), which is precisely FR7's "Feature-tier code changed without a corresponding spec delta" violation. The document asserts hook and CI "behave identically" by construction, but hook mode is scoped to *this commit's* staged diff while CI mode is scoped to the *whole PR diff* — a spec delta earlier in the same branch would save the CI check but not the local hook. Nothing in the doc says `waypoint verify` bypasses its own hook (e.g., via `--no-verify` internally), and if it does that unstated, undocumented, it quietly reintroduces exactly the kind of unlogged bypass mechanism this round claims to have eliminated. As written, the most likely outcome is that `waypoint verify` cannot successfully complete its commit step on a Feature/System-tier spec's ledger, which breaks the entire replacement mechanism at its core. *Fix:* explicitly add the ledger path pattern (e.g. `tasks/**` or `.waypoint/**`) to the default/required patch-tier globs so `gate()` never sees a ledger-only commit as needing a delta, or have `gate()` special-case `verify`'s internal commit (e.g., a documented, non-hidden `--no-verify` invocated only by `waypoint verify` itself, called out as an intentional non-bypass in the Error Handling Strategy so it isn't confused with Story 3.1 AC2's bypass case).

- **high** CI's "done-claim correctness" re-check has no bound and no incremental strategy (§ Components → Gate Script `runCheck()`; § Core Workflows step 7) — CI is specified to, "for every task the ledger already claims is `done` as of the PR's HEAD," re-run `check_command` (global, e.g. the whole `npm test` suite per Infrastructure) against that task's `linked_commit`. This is stated with no scoping to the current PR's changed specs and no caching/memoization of a result already validated by a prior CI run on the same commit SHA. Under NFR4's own stated ceiling (up to 50 open specs), a repo could easily accumulate 100s of `done` tasks; re-running a full test suite that many times on every single PR is a very different cost profile from the pre-commit `gate()` check NFR4 actually bounds (<2s) — and nothing in the document acknowledges this is a distinct, unbounded cost, or offers a strategy (e.g., skip tasks whose `linked_commit` is an ancestor of a commit CI has already validated) to keep it practical. Left unspecified, two builders could reasonably build very different CI runtimes here — one that's fine for a 10-task repo and unusable for a 200-task one. *Fix:* scope the re-check to tasks touched by the current PR's spec deltas (or a periodic/scheduled full sweep, analogous to `check-drift`), and/or specify a cache keyed by `linked_commit` SHA so a commit already validated by any prior CI run isn't re-verified again.

- **high** Bypass-logging story assumes a PR/branch-protection-capable git host that isn't actually pinned as an assumption, and may not hold for Waypoint's own stated primary user (§ Core Workflows "Bypass, reframed"; § Error Handling Strategy "Bypass"; cross-check PRD A4, brief.md Target Users) — the redesign's answer to Story 3.1 AC2 ("logged, not silent") is entirely "the git host's own protected-branch override audit trail... already satisfies this natively," citing GitHub/GitLab admin-override logs. That only applies when changes land through a PR that a required, branch-protection-gated CI check actually covers. PRD's A4 says only "git is the consuming repo's VCS" — it says nothing about a hosting platform, PR workflow, or branch protection being present, and brief.md's primary target user is explicitly "the developer building this (solo or small team)... using Claude Code / Cursor... day-to-day" — a profile at least as likely to commit straight to a default branch with no PR and no branch protection as to use a gated PR flow. In that direct-commit case, a local `git commit --no-verify` bypass is completely silent: no Waypoint log (removed by design), no git-host audit trail (no PR was ever opened), and CI's re-check may never run at all if there's no CI trigger on direct pushes. Story 3.1 AC2 is not actually satisfied in this realistic, PRD-sanctioned scenario, and the document presents the bypass question as closed without surfacing this dependency. *Fix:* either add an explicit assumption (a new A5, or broaden A4) that Story 3.1 AC2's guarantee holds only under a PR + required-status-check workflow, and note the solo-direct-push case as an accepted gap (consistent with brief.md's target-user framing), or keep a minimal Waypoint-side local log (e.g., append a line to a local, gitignored bypass log) as a fallback for exactly that case.

- **medium** No specified failure/rollback contract for `waypoint verify`'s commit step (§ Core Workflows step 6; § Components → Gate Script) — the document says `runCheck()` success causes `verify` to write ledger fields + `.gate-state` hash, "then makes its own commit." It doesn't say: (a) what `verify` stages — only the ledger file, or whatever happens to be staged/dirty in the working tree at that moment (a real risk given the ledger commit is meant to be narrowly scoped); or (b) what happens if the commit step itself fails for any reason (the bootstrapping problem above, an unrelated pre-commit hook in the consuming repo, a merge conflict) — is the ledger left modified-on-disk-but-uncommitted, with a `.gate-state` hash already written for a `status: done` that was never actually committed? That's an inconsistent intermediate state the doc doesn't acknowledge exists or how to detect/recover from. *Fix:* specify that `verify` stages only the ledger file path itself (`git add <ledger-path>` scoped, never `-A`/`.`), and specify the rollback behavior on commit failure (e.g., revert the in-memory ledger write and hash before reporting failure, so a failed `verify` leaves the working tree exactly as it found it).

- **medium** `linked_commit`'s semantics are looser than FR6/Story 3.2 imply (§ Data Models → Task ledger; § Core Workflows step 6) — `linked_commit` is set to whatever `HEAD` is at the moment `waypoint verify <task-id>` happens to be invoked, not necessarily the commit that implemented that specific task. If an agent commits task t1's work, keeps working, commits more (now unrelated) changes, and only then runs `waypoint verify <spec-id> t1`, `linked_commit` for t1 points at a commit that also contains unrelated work. Combined with `check_command` being global rather than per-task (an already-accepted MVP tradeoff), this means `waypoint verify` mechanically confirms "the whole suite passes at some HEAD the human/agent chose to invoke verify at," not "this specific task's implementation, isolated, passes" — a materially weaker guarantee than FR6's "settable only... upon verified completion (e.g., linked commit + passing check)" language suggests. Not newly introduced by v0.4, but not addressed by it either, and worth being explicit about since this round is the one that finalized the verify command's contract. *Fix:* document this as an explicit accepted limitation (parallel to the existing global-`check_command` callout in Infrastructure), so a reader doesn't infer `linked_commit` is a tighter guarantee than it is.

- **low** Global `check_command` lets `verify` mark a not-actually-done task `done` (§ Infrastructure; cross-check PRD FR6/Story 3.2 AC2) — since `check_command` is one global command for the whole repo (explicitly accepted for MVP), `waypoint verify <spec-id> t2` succeeds whenever the full suite happens to pass at HEAD, even if no test exercises t2's work at all (e.g., t2 has no tests yet). This is a real, if already-acknowledged, gap in FR6's "an agent can't mark its own work complete without verification" guarantee — an agent can run `verify` against a task it hasn't actually implemented, as long as the suite is green for unrelated reasons. *Fix:* no change needed for MVP scope, but call this out explicitly as a known residual gap in FR6's guarantee (not just as a "global command, no override" scoping note), so it isn't mistaken for a closed issue.

## Dimension coverage check

The document covers the full expected structural dimension set: Introduction/scope, High-Level Architecture (with diagram), Tech Stack, Data Models (with explicit field-ownership table), Components, Core Workflows (per-tier flows plus drift-check), Source Tree (both the framework repo and a consuming repo post-install), Infrastructure & Deployment, Error Handling Strategy, and Test Strategy. Versioning/semver policy and cross-platform test-matrix scoping are both explicitly pinned. No dimension is missing outright. The gap in this round is not coverage breadth but depth on the one new mechanism (`waypoint verify`'s commit step) introduced to replace the removed subsystem — that piece needed the same scrutiny the old hook/trailer/CI-write path got in rounds 1–3 and didn't get it.

## PRD/brief cross-check

- **FR1–FR5, FR9–FR12**: consistent with architecture.md; no new divergence found this round.
- **FR6/Story 3.2** (ledger, gate-only-writer): mechanism is well-specified for *who* may write `done`/`verified_by_gate`/`linked_commit` (only `waypoint verify`), but the critical finding above means the mechanism may not be able to *commit* that write on a Feature/System-tier spec without failing its own gate — a direct threat to FR6 being deliverable as described. Story 3.2 AC2's "correctly transitions a task to `done` when its linked commit passes the specified check" is satisfiable in isolation but the housekeeping commit that must follow is where it breaks.
- **FR7/Story 3.1 AC1**: satisfied for the spec-delta-blocks-a-commit mechanism itself; AC2 ("logged, not silent") has the gap described in the bypass-logging finding above — it depends on a PR/branch-protection workflow that isn't pinned anywhere as a requirement, and may not match brief.md's stated primary (solo) user.
- **NFR4** (gate <2s on 2,000 files/50 specs): the bound is written narrowly enough to cover only the fast pre-commit `gate()` spec-delta check, and the document is internally consistent about that scope — but it leaves CI's second check (`runCheck()` over every `done` task) completely unbounded, which is the performance finding above. This is a PRD-scoping gap as much as an architecture one: NFR4 should either be broadened to say something about the CI re-check's cost, or a new NFR should cover it.
- **A4** ("git is the consuming repo's VCS"): technically not contradicted — the redesign is still git-specific. But the bypass-logging mechanism now depends on a *git hosting platform* with PR merges and admin-override audit logs, which is a materially narrower assumption than "git is the VCS" and isn't captured by A4 or any other Assumptions Index entry. This should be surfaced as its own assumption given how much of Story 3.1 AC2's satisfaction now rests on it.
- **A1–A3**: unaffected by this round's changes.
- Brief.md's proposed-solution point 3 ("a task-completion ledger the agent cannot self-report around") and Goals & Success Metrics' "100% of merged changes... have a corresponding spec delta — enforced by a gate, not a convention" are both put at risk by the critical finding, since a `waypoint verify` that can't complete its own commit is a mechanism that doesn't actually run end-to-end as designed.

**Severity count (double-checked): 1 critical, 2 high, 2 medium, 1 low — 6 findings total.**
